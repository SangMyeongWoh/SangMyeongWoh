    기업 문서 지식 Q&A 엔진
    MARGE 공동 개발

    MARGE는 회사 안에 흩어진 규정·정책·업무 문서를 읽고, 직원의 질문에 근거를 달아 답하는 RAG 기반 지식 Q&A 엔진입니다. 넷마블 사내 챗봇들과 외부 고객사 서비스(nDIS)가 이 엔진 위에서 돌아갑니다.

    엔진 전체를 개발자 2인이 처음부터 만들었습니다. 저는 그중 질문을 이해하고 → 문서를 찾고 → 답을 만드는 런타임 파이프라인을 담당했고, 2026년에는 에이전틱 구조 리뉴얼을 공동 설계하고 직접 구현했습니다. 문서 수집·인덱싱 파이프라인과 인프라는 동료가 담당했습니다.

    2024년 6월 시작부터 공동 개발했고, 리뉴얼 구현과 실측 검증까지 마친 뒤 MarbleAI 언어 파트 리딩으로 옮겨가면서, 지금은 동료가 주도해 고도화하고 있습니다.

    Problem1세대 MARGE의 한계 — 운영하며 발견한 것들

    1세대 엔진(하이브리드 검색 + 유형별 답변 생성)으로 사내 챗봇들을 2년 가까이 운영하면서, 고칠 수 없는 것이 아니라 구조를 바꿔야 풀리는 문제들이 쌓였습니다.

    • 01일방통행검색 한 번, 생성 한 번으로 끝나는 고정 파이프라인. 검색이 빗나가면 스스로 알아채지도, 다시 시도하지도 못했습니다.
    • 02검증 부재만들어진 답을 그대로 내보냈습니다. 근거가 부족한 답과 답하면 안 되는 질문을 거르는 최종 관문이 없었습니다.
    • 03비대해진 분석기질문 분류·검색·재정렬이 1,300줄짜리 한 덩어리에 얽혀, 기능을 하나 붙일 때마다 수정 범위를 예측하기 어려워졌습니다.
    • 04확장성새 지식 소스를 붙이려면 파이프라인 전체를 손봐야 했습니다.
    • 05품질 측정구조를 갈아엎었을 때 정말 나아졌는지 잴 방법이 없었습니다 — 정답지가 없는 챗봇이니까요.

    고정 파이프라인을 고쳐 쓰는 대신, 스스로 판단하고 다시 시도하는 구조로 재설계를 결정했습니다.

    Analyze & Apply분석 및 적용 — 에이전틱 재설계

    01일방통행계획 → 검색 → 생성 → 검증의 그래프 구조로 다시 설계했습니다. 검증이 "부족하다"고 판정하면 실패 원인을 진단해 계획부터 다시 시도합니다(최대 3회). 재시도가 이전 시도의 답에 끌려가지 않도록 시도마다 문맥을 격리했습니다.

    02검증 부재답이 나가기 전 검증자(Evaluator)를 최종 관문으로 세웠습니다 — 채택·재시도·차단을 판정하고, 차단이면 지어내는 대신 정형 거절문을 내보냅니다.

    03비대해진 분석기한 덩어리였던 분석기를 계획자·검색자·생성자·검증자 노드로 분해해 각자 한 가지 역할만 맡게 했습니다.

    04확장성검색자를 플러그인 구조로 바꿨습니다 — 계획자가 소스를 고르면 병렬로 실행되고, 새 소스는 등록만 하면 됩니다.

    05품질 측정구조 전환의 근거를 실측으로 만들었습니다 — 89문항 비교와 가드레일 50문항을 직접 설계·수행하고, 나아진 점만이 아니라 느려진 점·비결정성 같은 약점까지 그대로 문서화했습니다. 정답지 없이 채점하는 자동 평가 하네스는 제가 설계하고 초판을 구현한 뒤 동료가 이어받았습니다.

    구조는 갈아엎되, 쓰는 쪽은 아무것도 바꾸지 않게 — 기존 응답 형식 그대로의 호환 창구를 함께 만들었습니다.

    Deep Dive내가 만든 것들

    1세대 엔진 — 질문 분석기·답변 생성기직접 구현
    • 멀티턴 재작성: 대화 이력을 참고해 생략된 질문을 완전한 질문으로 복원.
    • 하이브리드 검색 융합: 벡터·키워드(BM25) 검색을 동시에 돌리고 결과를 RRF로 합산.
    • LLM 리랭킹: 후보 문서의 관련성을 LLM이 재판정 — 병렬 실행으로 응답 시간 절감.
    • 7가지 답변 전략: 즉답(FAQ) · 근거 요약 · 문서 집계 리포트 · 메타 질문 · 잡담 · 정형 거절 · 사과 — 질문 유형에 따라 분기.
    • 인용 후처리: 답변 문장에 출처 문서를 연결하고, 담당자 정보를 정리해 함께 제공.
    에이전틱 리뉴얼 — 스스로 판단하고 다시 시도공동 설계 · 직접 구현
    • 계획–검색–생성–검증 그래프: 답을 만들기 전 계획을 세우고, 만든 답을 검증해 부족하면 실패 원인을 진단하고 다시 계획(최대 3회).
    • 시도 간 문맥 격리: 재시도가 이전 시도의 답을 보지 못하게 문맥을 끊어, 같은 실수에 끌려가는 것(앵커링)을 방지.
    • 검증자 최종 관문: 채택 · 재시도 · 차단 3판정 — 차단이면 지어내는 대신 정형 거절문.
    • 플러그인 검색자: 계획자가 고른 소스들을 병렬 실행 — 소스 하나가 죽어도 전체는 살아서 진행.
    • 호환 창구: 신형 엔진 위에 기존 응답 형식을 그대로 내보내는 창구를 얹어, 프론트를 고치지 않고도 전환할 수 있게.
    실측 검증 — 갈아엎은 근거 만들기직접 수행
    • 비교 평가 설계: 구형·신형 엔진을 같은 89문항(인사 50 · 총무 39)으로 비교 — 우위 20 · 동등 69 · 열위 0.
    • 가드레일 실측: 개인정보·금지 주제 50문항 — 유출은 양쪽 0건, 오탐은 구형 1건 · 신형 0건.
    • 정직한 기록: 응답이 1.5배 느려진 점, 같은 질문에 판정이 갈리는 비결정성 등 약점을 그대로 문서화해 전환 판단의 근거로.
    운영 개선 — 쓰이면서 생긴 요구들직접 구현
    • 동의어 관리 API: 사내 은어·약칭을 검색에 반영하도록 등록 창구 신설.
    • 집계 리포트 모드: 문서 여러 편을 섹션별로 요약해 하나의 리포트로 생성.
    • 메신저 연동: 웹 밖에서도 쓸 수 있게 사내 메신저(네이버웍스) 연동 앱 구축.
    • 운영 튜닝: 인용 오염 제거, 담당자 정보 후처리, FAQ 판정 임계값 조정 등 서비스 품질 개선 다수.
    함께 만든 것과 경계역할 구분
    • 공동: MongoDB 기반 검색 모듈, 프롬프트 자산, 에이전틱 리뉴얼의 설계 방향.
    • 동료 주도: 문서 수집·인덱싱 파이프라인(Airflow), API 골격과 인프라(GKE·Jenkins), 자동 평가 하네스의 이후 발전, 그리고 현재의 고도화.
