기업 문서 지식 Q&A 엔진
MARGE 공동 개발

MARGE는 회사 안에 흩어진 규정·정책·업무 문서를 읽고, 직원의 질문에 근거를 달아 답하는 RAG 엔진입니다.

2인이 처음부터 만들었습니다. 저는 그중 질문을 이해하고 → 문서를 찾고 → 답을 만드는 런타임 파이프라인을 담당했고, 2026년에는 에이전틱 구조 리뉴얼을 공동 설계하고 직접 구현했습니다. 문서 수집·인덱싱 파이프라인과 인프라는 동료가 담당했습니다.

제가 맡은 범위는 리뉴얼 구현까지입니다. 이후 고도화는 동료가 주도하고, 지금은 방향을 함께 논의하는 것으로 참여합니다.

Problem1세대 MARGE의 한계 — 운영하며 발견한 것들

1세대 엔진(하이브리드 검색 + 유형별 답변 생성)으로 사내 챗봇들을 2년 가까이 운영하면서, 고쳐서는 풀리지 않고 구조를 바꿔야 하는 문제들이 쌓였습니다.

  • 01일방통행검색 한 번, 생성 한 번으로 끝나는 고정 파이프라인. 검색이 빗나가면 스스로 알아채지도, 다시 시도하지도 못했습니다.
  • 02검증 부재만들어진 답을 그대로 내보냈습니다. 근거가 부족한 답과 답하면 안 되는 질문을 거르는 최종 관문이 없었습니다.
  • 03한 덩어리 코드질문 분류·검색·재정렬이 1,300줄짜리 한 덩어리에 얽혀, 기능을 하나 붙일 때마다 수정 범위를 예측하기 어려워졌습니다.
  • 04확장성새 지식 소스(문서·FAQ·담당자 정보 등)를 붙이려면 파이프라인 전체를 손봐야 했습니다.

고정 파이프라인을 고쳐 쓰는 대신, 스스로 판단하고 다시 시도하는 구조로 재설계를 결정했습니다.

Analyze무엇을 놓고 무엇을 골랐나

01일방통행ADK 1.x는 에이전트를 계층으로 쌓아 실행하는 구조라 검사 결과에 따라 계획으로 되돌아가는 흐름을 만들 수 없었습니다. 2.0에서 노드 · 조건부 분기 · 순환이 프레임워크에 들어오면서, Planner(계획) → Retriever(검색) → Generator(생성) → Evaluator(검증) 그래프로 다시 설계했습니다. 검증이 "부족하다"고 판정하면 실패 원인을 진단해 계획부터 다시 시도합니다(최대 3회).

02검증 부재답이 나가기 전 마지막 관문으로 Evaluator를 뒀습니다. 답을 그대로 내보낼지 · 다시 시도할지 · 막을지 판정합니다.

03한 덩어리 코드1,300줄을 정리하는 대신, 뒤엉켜 있던 역할을 Planner · Retriever · Generator · Evaluator 네 개로 쪼개 각자 한 가지 일만 하게 했습니다.

04확장성Retriever를 소스별 모듈로 분리했습니다. Planner가 필요한 소스를 고르면 병렬로 실행되고, 새 소스는 모듈만 등록하면 붙습니다.

Action무엇을 만들고 무엇을 감수했나

01일방통행변경된 설계로 답변 시간이 지연되었습니다. 실측에서 응답이 1.5배 느려진 대신, 좀 더 똑똑한 RAG 챗봇 경험을 유저에게 제공합니다. 느려진 시간은 UI/UX에서 중간 과정을 유저에게 공유하는 것으로 대신합니다.

04확장성소스를 병렬로 돌리면서 하나가 죽어도 나머지로 답을 만들게 했습니다. 근거 하나가 빠진 채 답이 나갈 수 있지만, 질문 전체를 실패시키는 것보다 낫다고 봤습니다.

Deep Dive

1세대 엔진직접 구현
  • 멀티턴 재작성: 대화 이력을 참고해 생략된 질문을 완전한 질문으로 복원.
  • 하이브리드 검색 융합: 벡터·키워드(BM25) 검색을 동시에 돌리고 결과를 RRF로 융합.
  • LLM 리랭킹: 후보 문서의 관련성을 LLM이 재판정. 병렬 실행으로 응답 시간을 줄였습니다.
  • 7가지 답변 전략: 즉답(FAQ) · 근거 요약 · 문서 집계 리포트 · 메타 질문 · 잡담 · 정형 거절 · 사과. 질문 유형에 따라 분기합니다.
  • 인용 후처리: 답변 문장에 출처 문서를 연결하고, 담당자 정보를 정리해 함께 제공.
에이전틱 리뉴얼공동 설계 · 직접 구현
  • 시도 간 문맥 격리: 재시도가 이전 시도의 답을 보지 못하게 문맥을 끊어, 같은 실수에 끌려가는 것을 방지.
  • Evaluator — 마지막 관문: 답을 그대로 내보낼지 · 다시 시도할지 · 막을지 세 가지로 판정합니다. 막을 때는 지어내는 대신 정해진 거절문을 내보냅니다.
이후 고도화 — 리뉴얼 골격 위에서동료 주도
  • 검증 4판정: "재생성"(검색은 그대로, 답만 다시) 분기를 추가해 검색 문제와 생성 문제를 분리했습니다. 값싼 수선을 먼저 시도합니다.
  • 검색 루프: 답을 만들기 전 Planner가 "더 찾을까, 충분한가"를 스스로 판단하며 반복 검색합니다. 재시도 왕복을 검색 단계 안으로 당겼습니다.
  • 되묻기: 대상을 특정할 수 없는 질문엔 답 대신 되묻습니다(프로젝트별 선택).
  • 문서 지도: 폴더·제목 색인을 LLM 호출 없이 렌더해 검색이 지식베이스의 실제 구조를 보고 조준하게 합니다.
  • 이 확장 전부가 리뉴얼 때 깐 그래프·상태 스키마 골격의 수정 없이 얹혔습니다.
실측 검증 — 전환 시점직접 수행
  • 비교 평가 설계: 전환 시점에 구형·신형 엔진을 같은 89문항(인사 50 · 총무 39)으로 비교 — 우위 20 · 동등 69 · 열위 0.
  • 가드레일 실측: 개인정보·금지 주제 50문항 — 유출은 양쪽 0건, 오탐은 구형 1건 · 신형 0건.
  • 약점도 기록: 응답이 1.5배 느려진 점, 같은 질문에 판정이 갈리는 문제까지 그대로 남겨 전환 판단의 근거로 삼았습니다.
