MARGE(MAgellan RaG Engine)

MARGE는 넷마블의 사내 RAG 엔진입니다.

2인 프로젝트의 주담당으로 엔진 설계 · 기획 · 구현과 서비스 운영을 맡았습니다. 질문 이해부터 검색 · 리랭킹 · 답변 생성, 문서 충돌 감지까지 직접 만들었고, 문서 수집 · 인덱싱 파이프라인과 인프라는 동료가 주도했습니다.

본 문서에서는 단일 플로우 RAG로 시작한 1세대 MARGE를 주로 이야기합니다. 현재의 MARGE는 에이전틱 리뉴얼을 거친 2세대입니다.

Problem

  • 01질의 다양성대화 중에는 잡담도 들어오고, 문서에 없는 것도 물어보고, 앞말을 생략한 질문도 들어옵니다. 질문마다 필요한 처리가 다른데, 하나의 흐름에 다 태우면 엉뚱한 답이 나갑니다.
  • 02질의-문서 불일치유저의 질문은 보통 길거나 짧은 문장 형태지만 실제 문서는 그렇게 구성되어 있지 않습니다. RRF로 검색을 구현할 때, BM25는 단어 간 비교가 기본이기 때문에 문제 없지만 벡터 비교는 정확도가 떨어질 수 있습니다.
  • 03컨텍스트 초과LLM은 모든 입력 컨텍스트를 온전히 이해하기 어려워합니다. 검색 결과가 많으면 반드시 필터링을 통해 컨텍스트 조절을 해줘야 합니다.
  • 04문서 전처리RAG에 입력되는 문서는 길이가 불규칙합니다. 한 번에 수십만 토큰으로 구성된 문서를 통째로 LLM에 넣을 수는 없으므로, 반드시 문서를 자르는 과정이 필요합니다.
  • 05문서 충돌같은 내용을 다룬 문서끼리 서로 반대되는 정보를 가진 경우가 있습니다. 검색이 올바른 경우에도 원본이 잘못되면 답변에 노이즈가 생길 수 있습니다.

Analyze설계 판단

01질의 다양성모든 질문에 대해 파이프라인을 태우기 전 LLM 기반 분석을 진행합니다.

02질의-문서 불일치청킹 때 LLM으로 각 조각의 예상 질문(Q-cluster)을 미리 생성해 두고 질문을 질문에 매칭해, 문장끼리의 비교로 벡터 정확도를 확보했습니다. 크로스인코더는 도메인별로 파인튜닝 및 서빙할 인력 부족으로 제외했습니다.

03컨텍스트 초과04문서 전처리두 단계로 컨텍스트를 조절합니다. 검색된 조각은 LLM이 한 번 더 선별(필터링)해 무관한 조각을 떨어내고, 그래도 많으면 하위 조각 요약을 상위 조각으로 반복 취합(계층 취합)합니다. 전처리에서는 고정 길이로 자르는 대신 시맨틱 청킹을 택했습니다(Lumberchunker 논문 참조). 우선순위는 내용 누락이 없을 것, 그다음이 의미 단위로 잘릴 것. 청킹 때 각 조각의 예상 질문(Q-cluster)도 함께 생성합니다.

05문서 충돌충돌 탐지용 별도 파이프라인을 새로 만드는 대신 엔진 부품을 재사용했습니다. Q-cluster로 관련 조각을 모으고, 조각별로 같은 질문에 각각 답하게 한 뒤 상반된 답을 낸 원본 문서를 찾아 사용자에게 경고합니다.

Action구현

01질의 다양성대화 이력으로 생략을 복원하는 멀티턴 재작성, 답의 모양을 정하는 질문 유형 분류, 잡담 · 고정 답변 · 범위 밖을 골라내는 분류를 구현했습니다. 유형에 따라 7가지 답변 전략(즉답 · 근거 요약 · 문서 집계 리포트 · 메타 질문 · 잡담 · 정형 거절 · 사과)으로 분기시키고, 답변 문장마다 출처 문서를 연결하는 인용 후처리를 붙였습니다.

02질의-문서 불일치RRF 융합을 자체 구현하고, 원본 질의와 재작성 질의를 병렬로 검색해 합쳤습니다. 고유명사 사전과 고유명사 그래프를 구축해 질의 재작성 · 검색 · 답변 생성에 공급했습니다. 새 조직 · 용어가 생길 때마다 사전과 그래프 갱신이 운영 업무로 남는 것은 감수했습니다.

03컨텍스트 초과검색된 후보를 LLM이 병렬로 재판정하게 해 지연을 눌렀고, 호출 수가 늘어 비용이 증가하는 것은 품질과 맞바꾼 대가입니다. 검색 결과가 많으면 계층 취합으로 컨텍스트 한도 안에서 누락 없이 답을 만듭니다.

04문서 전처리청킹 파이프라인 구현은 동료가 주도하고 저는 보조했습니다. 청킹 때 각 조각의 예상 질문(Q-cluster)이 함께 생성되어 검색 자산으로 쌓입니다.

05문서 충돌충돌 감지는 만들고 나서 배운 쪽입니다. 실사용에서 들어오는 팀 대부분이 이미 잘 관리된 문서를 가져왔고, 문서가 바뀔 때마다 다시 돌려야 해 LLM 비용 대비 효용이 낮았습니다. 접는 판단을 했고, 지금의 LLM 성능이면 별도 시스템 없이 답변 생성 단계에서 충돌을 함께 다루는 게 맞다고 봅니다.

Renewal이후 전개 — 에이전틱 리뉴얼

1년 반을 운영하고 회고하면서 리뉴얼이 필요하다고 제가 제기했습니다. 고정 플로우라 개선 요청을 받아내기 어려웠고, 프롬프트가 구세대 LLM 기준에 맞춰져 있었습니다. 충돌 감지에서 배운 것도 반영해, 별도 시스템 대신 답변을 만들 때 충돌 위험을 함께 감지하는 방향으로 잡았습니다.

2026년, 계획 → 검색 → 생성 → 검증의 에이전틱 그래프 구조로 리뉴얼했습니다. 설계는 공동, 저는 런타임 파이프라인 구현을 맡았습니다. 전환 검증은 1세대에서 만든 89문항 GT를 그대로 사용했습니다 — 우위 20 · 동등 69 · 열위 0, 가드레일 50문항에서 유출 양쪽 0건. 응답이 1.5배 느려진 것은 중간 과정을 보여주는 UX로 흡수했습니다. 이후 고도화는 동료가 주도합니다.

Future Work검색과 평가

지금 MARGE의 검색은 벡터와 키워드(BM25)를 동시에 돌려 RRF로 합치는 하이브리드 방식입니다. 답을 만들기 전 근거가 모일 때까지 검색을 반복하는데, 이 왕복이 응답 시간을 그대로 늘립니다. 그리고 이 검색 스택은 2024년의 선택지입니다. 지금 다시 고른다면 크로스인코더 리랭커와 최신 임베딩부터 재평가할 것이고, 그 재평가가 아래 방향과 이어집니다.

한 번에 제대로 찾아 검색 루프 자체를 줄이는 것을 목표로 하고 있습니다. 두 갈래를 놓고 검토 중입니다. 하나는 문서와 개념을 관계로 이어 그래프로 검색하는 방식(GraphRAG)이고, 다른 하나는 원문을 미리 읽어 OpenWiki 방식처럼 항목 단위로 재구성하는 방식입니다.

평가도 넓히려 합니다. 프로젝트마다 붙는 검색 소스가 달라서, 어떤 소스를 어떤 순서로 거쳤는지 보는 트래젝토리 평가는 공통으로 만들기 어렵습니다. 1세대에서 세운 GT 기반 판정처럼, 최종 답만 놓고 재는 E2E 판정을 프로젝트별로 맞춰 붙이는 쪽을 목표로 두고 있습니다.

Deep Dive

시스템 구성판단 · 패키지 직접, 구성은 보조
  • GKE: 상시 서빙되는 챗봇과 상주 구성요소가 있는 워크로드라 GKE를 택했습니다. 간헐 배치인 MaMT를 Cloud Run에 올린 것과 반대 판단입니다. 클러스터 구성과 배포(Jenkins CI/CD)는 동료가 주도하고 저는 보조했습니다.
  • LLM 호출 공통 패키지: 멀티 프로바이더를 같은 방식으로 부르고, 모든 입출력이 메타정보와 함께 GCS에 적재되게 했습니다. 디버깅과 품질 판정이 이 로그 위에서 돌아갑니다.

실측 검증 — 전환 시점직접 수행
  • 판정기: 1세대에서 89문항 GT에 대한 LLM 판정기를 구축해 엔진을 고칠 때마다 품질을 쟀습니다. 리뉴얼 전환 검증도 같은 판정기로 진행했습니다.
  • 비교 평가: 오래 운영된 HR 챗봇의 기존 GT 89문항(인사 50 · 총무 39)으로 구형·신형을 같은 기준에서 비교 — 우위 20 · 동등 69 · 열위 0.
  • 가드레일 실측: 개인정보·금지 주제 50문항. 유출은 양쪽 0건, 오탐은 구형 1건 · 신형 0건.
  • 약점도 기록: 응답이 1.5배 느려진 점, 같은 질문에 판정이 갈리는 문제까지 그대로 남겨 전환 판단의 근거로 삼았습니다.
