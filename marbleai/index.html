배경과 역할

게임을 새로 해외에 런칭하거나 업데이트를 할 때마다 수만 문장을 각 나라의 언어 수만큼 번역해야 합니다. 사람 번역만으로는 일정도 비용도 맞출 수 없어 지금은 대부분을 LLM이 번역합니다. MaMT(Marble Machine Translation)는 이 번역을 맡는 시스템으로, 넷마블 사내 AI 플랫폼 MarbleAI의 번역 시스템입니다. 저는 MaMT의 AI 백엔드를 전담합니다.

MaMT를 전담하기 전 약 2년간 운영을 지원하며, 인프라 태그·few-shot 관리 용어집 평가 전반에 걸친 구조적 문제를 확인했습니다. 모든 처리가 단일 VM에서 이뤄지고 있어 개별 개선만으로는 한계가 있었고, 전담 이후 백엔드를 전면 재설계했습니다. 기계번역과 용어집 시스템은 직접 구현했으며, 평가 시스템은 팀원과 공동 개발했습니다. 원본 교정 시스템은 비슷한 시기에 팀원이 별도 구축했고, 현재는 이 네 시스템을 모두 맡아 운영하고 있습니다.

재설계로 해결한 문제

인프라

VM 한 대의 Airflow에서 Cloud Run으로

직접 구현

기존 백엔드는 VM 한 대에 Airflow를 올려 돌렸습니다. 처리 용량이 VM 한 대로 정해져 있어, 대량 작업이 들어와 워커를 다 차지하면 몇 문장짜리도 그 뒤에서 기다렸습니다.

워커와 Redis, DB가 VM 한 대의 메모리와 디스크를 나눠 써서, 한 작업이 자원을 과하게 쓰면 다른 작업에까지 영향을 미쳤습니다. 이로 인한 장애가 한 달에 몇 번씩 있었습니다.

VM은 사람이 직접 관리해야 했고, 워커 수평 확장을 위해 VM을 추가하기에는 운영 부담이 컸습니다.

배포는 자동화 없이 컨테이너를 직접 내렸다 올려야 해서, 진행 중인 번역이 없는 때를 골라야 했습니다.

번역 요청은 60%가 100문장 미만입니다. 평소에는 작은 요청이 이어지다가 한 번씩 수십만 문장이 몰리는 패턴입니다. 이 패턴에 맞으면서 운영 부담도 적은 환경을 찾아 Cloud Composer · GKE · Cloud Run을 비교했습니다.

Composer는 Airflow를 그대로 옮길 수 있고 직접 관리할 서버도 없어지지만, 요청이 없을 때도 환경 전체가 항상 떠 있어야 했습니다. 평소에 작은 요청 위주인 우리 번역 패턴에서는 효율성이 떨어진다고 판단해 제외했습니다.

GKE도 비슷했습니다. 노드 수를 피크에 맞춰 두면 낭비가 되고, 평소 수준에 맞춰 두면 피크마다 노드 확보 대기 시간이 너무 길었습니다. 뿐만 아니라 GKE는 클러스터를 직접 관리해야 하는 운영 부담까지 있었습니다.

반면 Cloud Run은 요청이 올 때만 컨테이너를 띄울 수 있었고, 클러스터 관리도 없었습니다. 리비전 교체 방식이라 진행 중인 번역을 끊지 않고 배포 역시 가능했습니다.

Cloud Composer

요청이 없어도 환경 전체가 항상 떠 있음

직접 관리할 서버는 없음

GKE

피크에 맞추면 낭비, 평소에 맞추면 피크마다 노드 확보 대기

클러스터를 직접 관리해야 함

Cloud Run

요청이 올 때만 컨테이너가 뜸

클러스터 관리 없음

번역 작업을 Cloud Run으로 옮겼습니다. 접수를 맡은 라우터가 문장 수와 언어 수를 곱해 작업 크기를 추정하고, 크기에 따라 경로를 나눕니다.

대부분을 차지하는 작은 작업은 콜드스타트를 겪지 않도록 상시 띄워 둔 Cloud Run Service가 바로 처리합니다. 큰 작업은 문장 묶음과 대상 언어 단위로 샤드를 나눠 Cloud Run Job을 여러 개 띄우고, 병렬로 번역합니다.

배포는 GitHub Actions로 자동화했습니다. Cloud Run은 새 리비전을 올려도 처리 중이던 요청을 끝까지 마치므로, 번역이 없는 때를 고를 필요가 없어졌습니다.

장애가 나면 작업 ID만 넣어 원인을 진단해 주는 스킬을 만들어, 장애 때마다 로그를 직접 읽던 일을 대신하게 했습니다. 이를 위해 라우터와 Service, Job, 샤드에 흩어지는 로그에 작업 ID를 넣고, 작업이 끝나면 ID 단위로 합쳐 둡니다.

아키텍처장애 진단

서버리스로 옮기면서 VM을 직접 관리하는 일이 없어졌고, 장애 진단 스킬로 인해 운영에 드는 사람 손이 줄었습니다.

작은 요청은 큰 작업과 처리 경로를 분리해, 큰 작업이 몰려도 그 작업이 끝나기를 기다리지 않고 바로 처리합니다.

작업마다 컨테이너가 따로 떠서, 한 작업이 자원을 많이 써도 다른 작업에 영향을 주지 않습니다.

진행 중인 번역을 중단하지 않고 배포할 수 있어, 번역 작업이 없는 시간을 따로 고를 필요가 없어졌습니다.

태그·few-shot 관리

태그 규칙 자동 생성, 문장 재사용, few-shot 개선 등

직접 구현
태그

새 게임을 연동할 때마다 사람이 태그 패턴을 찾아 정규식을 만들고 코드에 직접 추가해야 했습니다. 그렇게 쌓인 정규식이 수십 종에 달했지만, 그마저도 태그를 정확히 판별하지 못했습니다.

번역 과정에서 태그가 지켜지지 않을 때마다 사람이 규칙을 하나씩 보완해야 했고, 정규식으로 판별하기 어려운 태그는 few-shot 예시로 직접 넣어야 했습니다.

Translation Memory

번역 요청으로 들어오는 문장의 35%는 기존 번역에 이미 있는 문장이었습니다. 번역할 필요가 없는데도 번역 파이프라인을 그대로 타고 있어, 그만큼 비용이 낭비됐습니다.

few-shot

태그를 위한 예시 외에 few-shot으로 들어가는 것은 벡터 유사도만으로 찾은 유사 문장이 전부였습니다.

태그

기존 번역 파일에는 그 게임에서 실제로 사용한 태그 사례가 쌓여 있었습니다. 정규식을 사람이 계속 보완하는 대신, 이 자료로 게임별 규칙을 만들 수 있다고 판단했습니다.

Translation Memory · few-shot

이미 검수된 번역이 있는데 다시 LLM으로 번역하면 비용이 들고 표현도 달라질 수 있습니다. 그래서 재사용할 수 있는 번역을 먼저 찾아야 했습니다.

few-shot은 기존 번역을 그대로 쓰는 경우와 목적이 다릅니다. 번역에 참고할 예시를 고르는 일이므로, 단순한 유사도 점수만으로는 충분하지 않다고 판단했습니다.

태그

기존 번역 파일을 바탕으로 게임별 태그 규칙을 자동 생성하고 검증하는 전처리를 구현했습니다. 번역할 때는 이 규칙으로 태그를 보호하고, 번역 결과에서도 태그가 지켜졌는지 확인합니다.

LLM 기반 태그 규칙 생성
Translation Memory · few-shot

기존 번역과 일치하는 문장은 번역 파이프라인을 거치지 않고 재사용하도록 했습니다. 태그 값만 다른 문장도 기존 번역을 활용합니다.

재사용할 번역이 없으면 기존 번역에서 few-shot 예시를 고릅니다. 벡터 유사도뿐 아니라 문장에 실제로 겹치는 표현도 반영했습니다.

Translation Memory와 few-shot 선정게임별 전처리

더 이상 사람이 태그 규칙을 직접 작성하지 않습니다. 기존 번역 파일에서 LLM이 자동으로 태그 규칙을 추출하고 검증까지 끝냅니다.

기존 번역에 같은 문장이 있으면 번역 파이프라인 없이 그 번역이 그대로 나옵니다. 전체 입력의 35%가 이렇게 처리되어, 그만큼 번역·검사·리플렉션에 드는 LLM 호출이 발생하지 않습니다.

few-shot 예시도 번역할 문장과 실제로 겹치는 표현을 기준으로 선별합니다.

용어집

엑셀 관리에서 공통 API로

직접 구현
구조

기존 MaMT에서는 용어집을 엑셀 파일로 관리하고, 번역 요청이 들어올 때마다 파일을 다시 읽었습니다. 용어 매칭 로직도 기계번역 코드에 포함돼 있어, 매칭 방식을 조금만 수정해도 기계번역 전체를 다시 배포해야 했습니다.

용어 매칭

번역할 문장에서 용어집에 들어 있는 용어를 찾아야 합니다. 찾은 용어는 번역 프롬프트에 들어가 번역에 쓰입니다.

기존에는 문장에서 용어집에 등록된 단어와 글자가 일치하는 부분을 찾고, 앞뒤 글자만 확인해 용어인지 판단했습니다. 문맥을 보지 않아 동음이의어에 대한 처리가 되지 않았습니다.

구조

기계번역, 교정, 평가가 같은 용어집을 쓰더라도 용어를 찾는 방식이 다르면 결과가 달라집니다. 규칙을 바꿀 때마다 여러 시스템을 고쳐야 하는 문제도 있습니다. 그래서 용어집과 용어를 찾는 기능을 한 서비스에 두고, 각 시스템이 같은 API를 호출하도록 했습니다.

용어 매칭

용어집에는 아이템 이름처럼 정해진 번역을 써야 하는 단어가 들어 있습니다. 번역할 문장에서 그 단어를 찾아야 하지만, 글자가 같다고 항상 같은 뜻은 아닙니다. 예를 들어 “수정이 필요합니다”의 “수정”은 아이템일 수도, 내용을 고친다는 뜻일 수도 있습니다.

규칙으로 판단할 수 있는 것은 바로 처리하고, “수정”처럼 뜻이 헷갈리는 경우에만 LLM이 문맥을 보고 판단하게 했습니다. 이렇게 하면 찾은 단어마다 LLM을 호출하지 않아도 됩니다.

구조

엑셀로 관리하던 용어를 DB에서 관리하도록 바꾸고, 단일 Cloud Run Service에 용어 조회·매칭 API를 구현했습니다.

용어 매칭

원문 언어에 따라 용어를 찾는 방식을 나눈 match API를 구현했습니다. 한국어·일본어는 글자가 일치해도 뜻이 불분명한 경우를 따로 판정하고, 중국어·대만어와 영어는 각 언어의 표기 방식에 맞춰 용어를 찾습니다.

용어집

용어 매칭을 수정해도 기계번역·교정·평가를 다시 배포할 필요가 없습니다. 세 시스템이 같은 용어집 API를 사용하므로 동일한 기준으로 용어를 찾습니다.

용어를 DB에서 조회해, 번역 요청마다 엑셀 파일을 다시 읽지 않습니다.

원문 언어에 맞는 방식으로 용어를 찾고, 한국어·일본어의 동음이의어는 LLM이 문맥을 보고 판정합니다.

평가

외주 검수를 LLM 평가기로 대체

팀원과 공동 구현

품질 확인이 외주 검수(2주~한 달, 분기 1회)라, 모델을 바꿔도 다음 분기에야 결과를 알 수 있었습니다. 새 모델이 나와도 기존 모델보다 나은지 빠르게 확인할 수 없었습니다.

수년간 쌓인 외주 평가 결과에는 번역문마다 발견된 오류의 종류·심각도와 점수가 기록돼 있었습니다. 이를 살펴보니 태그 누락·숫자 불일치·미번역처럼 규칙으로 확인할 수 있는 오류와, 오역·내용 누락처럼 문맥을 읽어야 판단할 수 있는 오류가 나뉘었습니다.

따라서 LLM에는 문맥을 읽어야 찾을 수 있는 오류를 맡기고, 규칙으로 확인할 수 있는 오류와 점수 계산은 코드로 처리하기로 했습니다. LLM이 찾은 오류는 기존 평가지에 기록된 오류와 비교해 검증할 수 있었습니다.

기존 외주 채점 기준을 바탕으로 내부 번역 평가기를 만들었습니다. 태그·변수·숫자·미번역은 정해진 규칙으로 검사하고, 용어 누락·문법 오류·자연스러움은 LLM이 평가합니다. 확인된 오류를 기준표에 따라 점수로 계산하고, 문장별 감점 이유를 리포트로 제공합니다.

평가

번역 품질 검수를 더 이상 외주에 맡기지 않습니다. 필요할 때 내부 평가기로 번역 결과를 채점하고, 점수와 문장별 감점 이유를 리포트로 확인합니다.

새 모델이 나오면 기존 모델과 새 모델로 같은 문장을 번역해 같은 기준으로 바로 비교합니다. 그 결과를 바탕으로 언어쌍마다 점수가 가장 높은 LLM을 실제 번역에 사용합니다.

사용성

파일 등록·용어집 관리·번역 실행 개선

프리셋

프리셋은 엑셀의 헤더가 몇 행인지, 몇 번째 열이 어느 언어인지 시스템에 알려 주는 설정입니다. 시트 번역을 맡길 때도 용어집을 등록할 때도 이걸 사람이 직접 만들어야 했습니다.

이미지 용어집

원본 용어집에는 이미지가 들어 있는데 시스템이 이미지를 받지 못해서, 이미지를 지우고 다시 만들어 올려야 했습니다.

용어집 롤백

용어집은 수정이 수시로 일어납니다. 수정 이력은 남았지만 그 시점으로 되돌리는 기능이 없었습니다.

용어 자동 번역

용어집에 언어를 하나 추가하면 그 열이 통째로 비는데, 사람이 다 채워야 했습니다.

프리셋

게임마다 언어 코드 표기와 헤더 위치는 달랐지만, 입력 파일은 모두 엑셀이었습니다. 행·열로 구성된 형식이 정해져 있어, 규칙과 LLM을 조합하면 헤더와 언어 열을 자동으로 인식할 수 있다고 판단했습니다.

이미지 용어집

엑셀 안에서 이미지가 놓인 위치를 알 수 있으니, 원본 파일을 따로 가공하지 않고 용어와 이미지를 함께 DB에 적재할 수 있습니다.

용어집 롤백

용어집은 보통 수백~수천 항목이라, 저장 시점마다 전체를 스냅샷으로 남기고 복원 시 통째로 갈아 끼워도 부담이 작다고 판단했습니다. 스냅샷은 복원할 때만 읽으므로 DB 대신 GCS에 파일로 두기로 했습니다.

용어 자동 번역

새로 추가한 언어의 용어도, 기존에 등록된 다른 언어의 용어를 참고하면 LLM으로 초안을 만들 수 있습니다.

프리셋

기존 용어집과 번역 파일에서 언어 코드 표기를 모아 사전으로 만들었습니다. 헤더와 언어 열은 이 사전과 규칙으로 먼저 판별하고, 판별되지 않는 열만 LLM에 보냅니다. 시트 번역과 용어집 등록이 같은 인식 과정을 씁니다.

이미지 용어집

엑셀 파일 안의 XML에서 이미지가 놓인 행·열을 읽어, 그 위치의 용어에 이미지를 연결해 저장합니다. 재등록, 편집, 내보내기도 이 연결을 기준으로 동작합니다.

용어집 롤백

용어집이 바뀔 때마다 전체 용어와 시트·열 구조를 묶어 GCS에 저장합니다. 복원할 때는 용어집에 잠금을 걸어 편집을 막은 뒤 스냅샷으로 교체합니다.

용어 자동 번역

언어 열을 추가하고 자동 번역을 누르면 빈칸을 LLM이 번역합니다. 이때 같은 용어의 다른 언어 번역을 함께 보여 줍니다. 결과는 사용자가 확인한 뒤에 저장합니다.

시트 번역을 맡길 때도 용어집을 등록할 때도 프리셋을 만들지 않습니다. 여러 파일을 한 번에 올릴 수 있고, 헤더와 언어 열은 자동으로 인식합니다.

이미지가 들어 있는 용어집을 원본 그대로 등록합니다. 이미지를 지우고 다시 만들어 올리는 일이 없어졌습니다.

용어집을 저장 시점으로 되돌릴 수 있습니다.

새 언어를 추가하면 다른 언어의 용어를 참고해 빈칸의 번역 초안을 만들고, 사용자가 확인한 뒤 저장합니다.

기계번역직접 구현

기존 번역에 같은 문장이 있으면 그 번역을 그대로 쓰고, 없는 문장만 LLM으로 번역합니다(Translation Memory와 few-shot 선정). 번역 전에는 깨질 수 있는 태그를 가려두고 용어집·유사 문장·캐릭터 페르소나를 모아 프롬프트를 조립합니다. 번역 후에는 결과를 그대로 믿지 않고 검사와 리플렉션을 거칩니다.

  • 무결성 검사 · 리플렉션: 가려둔 태그가 그대로 돌아왔는지, 변수가 같은 수로 남았는지, 용어를 빠뜨리지 않았는지 코드로 검사합니다. 용어 검사는 용어집의 validate가 맡습니다. 실패한 항목만 LLM이 수정하고 다시 검사합니다. 루프가 끝나도 결함이 남으면 결함이 가장 적은 후보를 내보냅니다. 결과에 따로 표시하지는 않고, 이런 건은 로그에 남겨 얼마나 나오는지 봅니다.
  • 문장 묶기: 일정 구간 단위로 대화와 비대화를 분류하고 같은 성격끼리 붙여 한 번에 보냅니다. 분류에 실패한 구간은 비대화로 처리해 멈추지 않고 넘어갑니다.
  • 모델 라우팅: 언어쌍마다 평가기 점수가 가장 높은 LLM을 씁니다.

장애 진단직접 구현

작업 ID만 입력하면 관련 로그를 찾아 장애 원인을 분석하는 Claude Code 스킬을 만들었습니다. 장애가 날 때마다 로그를 직접 뒤져 원인을 추정하던 과정을 이 스킬로 자동화했습니다.

  • 로그 통합: 번역 한 건은 라우터와 Service, Job, 샤드를 거치며 로그가 흩어집니다. 모든 로그에 작업 ID를 넣고 같은 형식으로 남긴 뒤, 작업이 끝나면 ID 단위로 합쳐 GCS에 둡니다. GCP 로그 라우터는 시간 단위로 로그가 쌓여 서로 다른 작업이 뒤섞여 보이므로 사용하지 않았습니다.
  • 요약 파일: 로그를 합치면서 오류·경고가 발생한 줄 번호와 처리 단계·언어별 로그 구간을 인덱스로 정리하고, LLM 비용도 함께 기록합니다. 장애 진단 스킬은 이 파일을 먼저 읽고 필요한 로그 구간으로 바로 이동합니다.
  • 통합 로그가 없는 경우: 메모리 초과나 시간 초과로 컨테이너가 강제 종료되어 통합 로그가 생성되지 않으면, Cloud Logging에서 해당 컨테이너의 로그를 직접 확인합니다.
LLM 기반 태그 규칙 생성직접 구현

기존 번역 파일의 원문과 번역문을 비교해 게임별 태그 규칙을 만듭니다. 원문에서 [ ], { }, < >로 감싼 문자열을 후보로 모으고, 번역문에도 그대로 남아 있는지 확인해 태그와 일반 문구를 구분합니다. Claude가 이 결과로 규칙을 작성하고, Gemini가 전체 후보에 적용해 검증합니다. 오류가 있으면 Claude가 수정하고 Gemini가 다시 검사합니다.

      게임별 전처리직접 구현

      기계번역의 전처리 단계입니다. 기계번역이 프롬프트에 넣는 유사 문장·캐릭터 페르소나·대화 예시·태그 규칙이 만들어지는 곳입니다. 게임에 쌓인 기존 번역 파일을 한 번 처리해 두고, 이후 번역은 그 결과를 가져다 씁니다.

      • 전처리 결과물
        • 태그 규칙: LLM 기반 태그 규칙 생성 항목에서 설명합니다.
        • 캐릭터 페르소나: 캐릭터가 아닌 화자를 걸러낸 뒤, 캐릭터별로 대사를 모아 LLM이 말투 설명을 만들어 둡니다. 같은 화자의 번역이 입력으로 들어오면 번역 컨텍스트에 포함시킵니다.
        • 벡터 인덱스: 태그를 뺀 원문을 임베딩해 DB에 넣어 둡니다. 번역할 때 예시 후보를 찾는 데 씁니다. 그 가운데 무엇을 예시로 넣는지는 Translation Memory와 few-shot 선정 항목에서 설명합니다.
        • 대화 예시: 화자가 이어지는 구간을 대화 묶음으로 잘라 둡니다. 번역할 때 같은 캐릭터들이 등장하면 해당 대화 묶음을 컨텍스트에 넣어 활용합니다.
      • 결과는 파일 내용과 원문 언어로 만든 키로 GCS에 저장해 두고, 같은 파일이 같은 언어로 다시 들어오면 전처리를 건너뜁니다. 한 파일에 원문 언어가 여럿이면 언어별로 병렬로 만들고, 같은 파일을 동시에 요청해도 한 번만 만듭니다.
      • 전처리가 실패해도 본 번역은 그대로 진행하고, 완료 통보에 기존 번역 파일이 반영되지 않았다는 표시와 사유를 함께 보냅니다. 태그 규칙만 실패하면 공통 규칙으로, 벡터 인덱스만 준비되지 않으면 예시 없이 번역합니다.

      전처리 흐름

      용어집직접 구현

      match: 원문에서 용어 찾기

      match는 원문에서 용어집 용어를 찾아 용어와 번역을 돌려줍니다. 기계번역은 프롬프트에 넣고, 평가기는 LLM의 용어 사용 검사에 활용합니다. 한국어·일본어·중국어·대만어·태국어는 Aho-Corasick으로 원문에서 용어와 글자가 일치하는 위치를 찾습니다. 영어는 단어를 기본형으로 바꿔 비교합니다. 한국어·일본어에서는 앞뒤 글자로 후보를 걸러내고, 남은 애매한 후보는 LLM이 판정합니다.

      큰 용어집의 검색 구조(Aho-Corasick 오토마톤)는 매번 만들지 않고 메모리와 GCS에 저장해 용어가 바뀔 때만 다시 만듭니다.

      validate: 번역문에 용어가 들어갔는지 확인

      기계번역의 무결성 검사에서 match가 찾은 용어가 번역문에 쓰였는지 확인합니다. 번역할 때마다 LLM에 묻지 않고 규칙으로 판별해, 빠진 용어를 돌려줍니다. 지원하는 31개 번역 언어를 다루며, 러시아어처럼 어미가 바뀌는 언어는 기본형과 격변화 규칙으로 비교합니다.

      평가팀원과 공동 구현

      수년 전부터 국제 표준 MQM을 사내 기준으로 변환한 채점 체계가 이미 있었습니다. 기존에는 사람이 그 기준대로 기계번역 결과를 채점했고, 지금은 평가기가 같은 기준으로 채점합니다.

      평가 흐름

      평가기에는 원문과 번역문을 넣어 태그·변수, 숫자, 미번역, 용어 누락, 문법 오류와 자연스러움을 확인합니다. 태그·변수 검사에는 LLM 기반 태그 규칙 생성에서 만든 게임별 규칙을 쓰고, 숫자·미번역은 원문과 번역문을 규칙으로 비교합니다.

      용어 누락은 용어집의 match가 원문에서 찾은 후보를 LLM이 번역문과 대조해 판단합니다. 기계번역의 규칙 기반 validate와 판단 방식을 분리해, 평가가 번역 단계의 검사 결과를 그대로 재사용하지 않도록 했습니다. 문법 오류와 자연스러움도 LLM이 평가합니다. 확인된 오류는 기준표에 따라 감점합니다.

      • 합격선 근처 재채점: LLM 채점을 한 번 더 실행해 두 점수 중 낮은 쪽을 사용합니다. 두 점수의 차이가 크면 세 번째까지 채점해 중앙값을 사용합니다.

      검증 방법

      번역 품질 채점에는 하나의 정답이 없습니다. 같은 기준표로 같은 번역을 채점해도 숙련된 평가사끼리 점수가 갈립니다. 그래서 특정 평가사의 점수를 정답으로 놓지 않았습니다.

      대신 같은 번역에 대해 평가사들의 점수가 흩어지는 범위를 기준으로 삼았습니다. 예를 들어 평가사 세 명이 70점, 80점, 90점을 줬다면 평균은 80점이고 점수는 70~90점 사이에 흩어져 있습니다. 평가기의 점수도 이 범위 안에 들어오는 것을 목표로 평가기를 만들었고, 수년간 쌓인 외주 평가지와 대조해 범위 안에 들어오는 것을 확인했습니다.

      오류 항목도 같은 평가지로 확인했습니다. 평가사가 오류로 표시한 문장과 오류 종류를 평가기도 찾아내는지 비교했습니다.

      한계

      용어집의 match가 원문에서 놓친 용어는 평가할 후보에도 들어오지 않습니다. 태그 검사도 기계번역과 같은 게임별 규칙을 쓰므로, 규칙 자체가 놓친 태그는 평가에서도 발견하지 못합니다.

      사람끼리도 점수가 갈리는 만큼, 평가기 점수는 절대 판정이 아니라 모델 간 비교와 추세 확인에 씁니다.

      원본 교정팀원 구현

      한국어 원본의 오탈자·잘못된 용어는 번역을 거치면 모든 언어로 증폭됩니다. 번역 전에 이런 오류를 찾아 교정안을 제시합니다. 숫자가 든 변경은 통째로 거부하고(게임 데이터 보호가 교정률보다 우선), 사람이 문장별로 검토합니다.
