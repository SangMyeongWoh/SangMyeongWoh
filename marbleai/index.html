게임 데이터를 안전하게 옮기는 일

MarbleAI는 넷마블의 사내 AI 플랫폼이고, 언어파트는 그중 게임 현지화(다국어 번역)를 담당합니다. 게임 텍스트는 일반 문서와 달라서, 범용 번역기로는 해결되지 않는 제약이 있습니다.

제약 ① 태그

텍스트 안에 {itemName} 같은 코드 조각이 섞여 있습니다. 번역하다 태그가 깨지면 게임 자체가 오작동합니다.

제약 ② 용어 통일

같은 스킬명·아이템명이 파일마다 다르게 번역되면 유저가 혼란에 빠집니다. 수만 개 용어를 전 언어에서 일관되게 유지해야 합니다.

제약 ③ 말투·세계관

캐릭터마다 말투(페르소나)가 있고 세계관 고유 표현이 있습니다. 정확하기만 한 번역은 게임에서는 틀린 번역입니다.

제약 ④ 분량과 마감

업데이트마다 수천~수만 문장이 쏟아지고, 글로벌 동시 출시 일정에 맞춰 십수 개 언어가 한꺼번에 나가야 합니다.

P — Problem / 왜 중요했는가

글로벌 동시 출시의 필수 경로가
서버 1대 위 Airflow에 묶여 있었다

제가 합류했을 때 번역 전 과정은 가상머신 1대에서 docker-compose로 띄운 워크플로 엔진(Airflow) 하나로 돌고 있었습니다.

  • 배포하면 진행 중이던 번역 작업이 소실되고 롤백 경로가 없어, 출시 일정이 걸린 작업일수록 손대기 어려웠습니다.
  • 시스템에 번역 단계밖에 없어 품질 보증·용어 통일·검수가 전부 사람 손에 있었고, 품질 검수는 외주에 맡겨 결과까지 약 한 달이 걸렸습니다.
  • 어떤 번역이 언제 무슨 품질로 나갔는지 조회할 기록 자체가 없어, 장애가 나면 재현부터 해야 했습니다.
번역량이 늘수록 사람이 선형으로 더 필요한 구조였습니다. 다음 장은 당시 구조를 코드 기준으로 정리한 것입니다.

고통 ③ — 진짜 이유

워크플로가 없었다

모든 파이프라인이 예약 실행 없이 요청 단위로만 동작. 부하도 요청 빈도가 아니라 한 건의 크기로 온다 — 일정 기반 엔진(Airflow)이 전제하는 사용 형태가 아니었다.

검토한 플랫폼내 판단
① 관리형 Airflow (Cloud Composer)미채택 — 관리형이어도 Airflow 운영 부담은 그대로 남는다
② 쿠버네티스 (GKE)미채택 — 강력하지만 전담 관리 인력이 필요해, 팀 규모에 비해 운영 부담이 크다
③ Cloud Run + Cloud Tasks채택 — 기준은 운영 인력. 지속 가능한 건 "잘 튜닝된 인프라"가 아니라 "튜닝할 게 없는 인프라"

번역 앞뒤에 품질 단계를 세웠다

번역 뒤 — 평가 자동화

외주 검수를 자동 채점으로 완전 대체

외부 업체의 품질 검수(LQA)는 결과까지 약 한 달 — 번역량이 늘수록 기간과 비용이 함께 늘었습니다.

자동 채점 체계(LQE)를 직접 구축했습니다. 규칙 검사가 확정 오류를 먼저 잡고, LLM 심판이 나머지를 판정합니다. 자기 번역을 자기가 채점하는 편향을 피하려 번역과 다른 모델을 씁니다.

→ 품질 검증: 약 1개월 → 자동
번역 앞 — 원본 교정 신설

오류의 다국어 증폭을 앞단에서 차단

일정에 쫓긴 한국어 원본의 오탈자·잘못된 용어는 그대로 번역하면 번역하는 모든 언어로 증폭됩니다.

LLM 3단계 호출(탐지→교정→리뷰)로 원본을 먼저 고치고, 숫자가 든 변경은 통째로 거부해 게임 데이터를 보호하며, 최종 채택은 사람이 문장별로 확정합니다.

→ 기존에 없던 단계를 새로 만듦
Quality
Deep Dive / 평가기 — 사람 검수를 대체하려면

신뢰할 수 있는 채점은 구조에서 나온다

확실한 것은 규칙이 잡고, 애매한 것만 LLM이 판정하며, LLM의 판정도 그대로 믿지 않습니다. 언어마다 아래 과정을 반복해 점수를 냅니다.

단계하는 일
① 규칙 검사태그 훼손·미번역·숫자 불일치·표기·지역 표기 규칙 5종을 LLM 없이 기계적으로 확정
② 용어 대조번역문이 지정 용어를 썼는지 용어집 API로 대조 — 굴절형·복합어까지 인정한 결과를 심판의 판단 근거로 제공
③ LLM 심판원문·번역을 5문장 창으로 대조해 오역·누락·문법 등 오류 유형 탐지 — 넓게 탐지한 뒤 재분류로 교정하는 2단 구조
④ 근거 검증심판이 문제 삼은 용어가 실제로는 지정 표기를 쓰고 있으면 그 주장을 기각 — "용어집이 권위". 근거 없는 일관성 지적도 기각
⑤ 감점 수식번역 품질 국제 표준 분류(MQM) 기반 13개 항목 — 분량으로 보정하고 중복 감점을 억제해 점수 산출
⑥ 경계 재채점합격선 근처 점수는 2~3회 다시 채점해 중앙값·보수값을 채택 — 점수 요동 방지
결정 ① 심판 ≠ 번역자

채점 모델을 번역 모델과 다른 계열로 분리 — 자기가 한 번역을 후하게 주는 편향을 구조로 차단.

결정 ② 규칙 먼저, LLM은 나중

확정 가능한 오류를 규칙 층에서 끝내 재현 가능성을 확보하고 LLM 비용·변동성을 줄임.

결정 ③ 게임 특화 정책

고유명사의 번역 선택은 감점 금지(공식 표기는 용어집만 안다). 치명 오류 판정은 보상·결제 오역 등 3가지로 제한해 과잉 감점을 막음.

Systems / 4개 시스템 설계 포인트

각 시스템에서 내가 내린 설계 결정

01 — 번역

태그·용어·말투 반영 다국어 번역. 언어 조합별 모델 라우팅 + 자동 폴백을 설계하고, 복수 클라우드 LLM 백엔드(Google Vertex·AWS Bedrock)를 운영. 대화 맥락은 청크 분할 + 예시 주입(few-shot)으로 보존.

02 — 교정

LLM 3단계 호출(탐지→교정→리뷰) 구조를 설계. 숫자 변경 통째 거부로 게임 데이터를 보호하고, 4개 시스템 중 유일하게 재실행-안전(멱등) 구조로 재시도를 허용.

03 — 용어집

문자열 다중 검색(Aho-Corasick)과 단어 원형(lemma) 분석을 함께 쓰는 이중 매칭 엔진. 리뉴얼 전에는 엑셀 파일을 매번 읽어 검색 구조를 즉석에서 만들었는데, 지금은 세 시스템이 호출하는 공용 서비스로 분리.

04 — 평가

규칙 검사가 확정 오류를 먼저, LLM 심판이 나머지를 판정하는 2단 구조. 번역과 다른 모델을 기본으로 두어 자기 채점 편향을 회피. 업계 표준 품질 분류(MQM) 기반 감점 체계.
