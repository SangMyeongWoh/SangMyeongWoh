프로젝트 소개

게임 한 편을 전 세계에 내보내려면 수만 문장을 최대 31개 언어로 옮겨야 합니다. 사람 번역만으로는 비용도 시간도 감당할 수 없어, 일부 메이저 언어를 제외한 대부분을 LLM 기반 기계번역이 맡고 있습니다. 최근에는 메이저 언어까지 기계번역을 도입하는 추세입니다. MarbleAI는 사내 게임 로컬라이제이션 AI 플랫폼으로, 음성과 언어 두 파트로 이루어져 있습니다. 저는 언어 파트(MaMT, Marble Machine Translation)의 AI 백엔드를 담당합니다.

1세대 MaMT에서는 2년여간 운영을 보조하는 역할이었습니다. 이후 MaMT를 전담하게 되었고, 운영하면서 지켜봐 온 문제가 인프라 태그·few-shot 관리 용어집 평가 전반에 걸쳐 있어 백엔드 전면 재설계를 진행했습니다.

문제 해결

인프라

VM 한 대의 Airflow에서 Cloud Run으로

직접 구현

1세대는 VM 한 대에 Airflow를 올려 돌렸습니다. 처리 용량이 VM 한 대로 정해져 있어, 대량 작업이 들어와 워커를 다 차지하면 몇 문장짜리도 그 뒤에서 기다렸습니다.

워커와 Redis, DB가 VM 한 대의 메모리와 디스크를 나눠 써서, 한 작업이 자원을 과하게 쓰면 다른 작업에까지 영향을 미쳤습니다. 이로 인한 장애가 한 달에 몇 번씩 있었습니다.

VM은 사람이 직접 관리해야 했고, 용량을 늘리려고 VM을 추가하기에는 운영 부담이 컸습니다.

배포는 자동화 없이 컨테이너를 직접 내렸다 올려야 해서, 진행 중인 번역이 없는 때를 골라야 했습니다.

번역 요청은 60%가 100문장 미만입니다. 평소에는 작은 요청이 이어지다가 한 번씩 수십만 문장이 몰리는 패턴입니다. 이 패턴에 맞으면서 운영 부담도 적은 환경을 찾아 Cloud Composer · GKE · Cloud Run을 비교했습니다.

Composer는 Airflow를 그대로 옮길 수 있고 직접 관리할 서버도 없어지지만, 요청이 없을 때도 환경 전체가 항상 떠 있어야 했습니다. 평소에 작은 요청 위주인 우리 번역 패턴에서는 효율성이 떨어진다고 판단해 제외했습니다.

GKE도 비슷했습니다. 노드 수를 피크에 맞춰 두면 낭비가 되고, 평소 수준에 맞춰 두면 피크마다 노드 확보 대기 시간이 너무 길었습니다. 뿐만 아니라 GKE는 클러스터를 직접 관리해야 하는 운영 부담까지 있었습니다.

반면 Cloud Run은 요청이 올 때만 컨테이너를 띄울 수 있었고, 클러스터 관리도 없었습니다. 리비전 교체 방식이라 진행 중인 번역을 끊지 않고 배포 역시 가능했습니다.

Cloud Composer

요청이 없어도 환경 전체가 항상 떠 있음

직접 관리할 서버는 없음

GKE

피크에 맞추면 낭비, 평소에 맞추면 피크마다 노드 확보 대기

클러스터를 직접 관리해야 함

Cloud Run

요청이 올 때만 컨테이너가 뜸

클러스터 관리 없음

번역 작업을 Cloud Run으로 옮겼습니다. 접수를 맡은 라우터가 문장 수와 언어 수를 곱해 작업 크기를 추정하고, 크기에 따라 경로를 나눕니다.

대부분을 차지하는 작은 작업은 콜드스타트를 겪지 않도록 상시 띄워 둔 Cloud Run Service가 바로 처리합니다. 큰 작업은 문장 묶음과 대상 언어 단위로 샤드를 나눠 Cloud Run Job을 여러 개 띄우고, 병렬로 번역합니다.

배포는 GitHub Actions로 자동화했습니다. Cloud Run은 새 리비전을 올려도 처리 중이던 요청을 끝까지 마치므로, 번역이 없는 때를 고를 필요가 없어졌습니다.

장애가 나면 작업 ID만 넣어 원인을 진단해 주는 스킬을 만들어, 장애 때마다 로그를 직접 읽던 일을 대신하게 했습니다. 이를 위해 라우터와 Service, Job, 샤드에 흩어지는 로그에 작업 ID를 넣고, 작업이 끝나면 ID 단위로 합쳐 둡니다.

아키텍처장애 진단

서버리스로 옮기면서 VM을 직접 관리하는 일이 없어졌고, 에러진단 스킬로 인해 운영에 드는 사람 손이 줄었습니다.

작은 요청은 큰 작업과 다른 경로로 처리되어 기다리지 않습니다.

작업마다 컨테이너가 따로 떠서, 한 작업이 자원을 많이 써도 다른 작업에 영향을 주지 않습니다.

배포는 진행 중인 번역을 끊지 않아, 시점을 고르지 않고 합니다.

태그·few-shot 관리

기존 텍스트 전체를 자동으로 전처리

직접 구현
태그

게임을 새로 붙이려면 사람이 태그 패턴을 찾아 정규식을 짜서 코드에 직접 넣어야 했습니다. 정규식 패턴 수십 종이 그렇게 쌓여 있었고, 그마저도 정확하지 못했습니다.

번역에서 태그가 지켜지지 않는 일이 많았고, 그때마다 사람이 규칙을 하나씩 추가해야 했습니다. 정규식으로 제대로 판별하지 못하는 태그는 사람이 few-shot 예시로 직접 넣어 주어야 했습니다.

Translation Memory

기존 번역에 동일한 문장이 있으면 번역할 필요가 없는데도, 번역 파이프라인을 그대로 타고 있었습니다.

few-shot

태그를 위한 예시 외에 few-shot으로 들어가는 것은 벡터 유사도만으로 찾은 유사 문장이 전부였습니다.

태그

사람이 찾아 넣던 태그 패턴은 전부 그 게임의 기존 번역 파일 안에 이미 들어 있었습니다.

괄호 모양만으로는 태그인지 알 수 없습니다. 대괄호 안에는 태그도 있고 일반 글자도 있습니다. 하지만 번역과 나란히 놓으면 구분됩니다. 번역되지 않고 그대로 남은 것이 태그입니다.

Translation Memory · few-shot

같은 문장이 이미 번역되어 있다면, 그것은 번역할 대상이 아니라 찾아서 그대로 쓸 대상입니다.

완전히 일치하는 문장만이 아닙니다. {0}개의 {1}을(를) 획득했습니다.와 {3}개의 {7}을(를) 획득했습니다.처럼 문장은 같고 태그 값만 다른 경우에도 기존 번역을 그대로 써야 합니다.

벡터 유사도는 비슷한 정도를 점수로 줄 뿐, 이런 형태의 같은 문장인지는 가려 주지 않습니다.

few-shot도 마찬가지입니다. 임베딩 모델은 학습 방식에 따라 유사도 비교에 취약점이 있을 수밖에 없습니다. 특히 문장이 짧거나 특수문자가 포함되어 있으면 뜻이 전혀 다른 문장끼리도 높은 점수가 나오기도 했습니다.

벡터 유사도만으로 예시를 골라서는 안 된다고 판단했습니다.

태그

기존 번역 파일을 등록하면 전처리에서 태그 규칙을 만듭니다. 기존 번역 파일은 그 게임에서 이미 번역해 둔 문장들로, 한 줄마다 원문과 그 번역문이 나란히 들어 있습니다.

원문에서 [ ], { }, < >로 감싸인 문자열을 태그 후보로 전부 뽑고, 같은 줄의 번역문에서 그 문자열이 어떻게 되었는지 봅니다. 번역문에도 글자 그대로 남아 있으면 태그이고, [길드]가 [Guild]로 바뀐 것처럼 번역되어 있으면 일반 글자입니다.

이렇게 가려낸 태그로 Claude가 규칙을 작성합니다. Gemini가 후보 전체로 검증해 틀린 곳을 고칩니다.

LLM 기반 태그 규칙 생성
Translation Memory · few-shot

번역할 문장마다 기존 번역에서 먼저 같은 문장을 찾습니다. 있으면 번역 파이프라인 없이 바로 결과로 내보냅니다. 태그 값만 다른 같은 틀의 문장도 값을 바꿔 넣어 그대로 씁니다.

같은 문장이 없으면 같은 기존 번역에서 예시를 고릅니다. 벡터 유사도만 보지 않고, 번역할 문장과 글자가 실제로 겹치는 정도로 다시 골라냅니다[1].

Translation Memory와 few-shot 선정

[1]M. Bouthors, J. Crego, and F. Yvon, “Retrieving Examples from Memory for Retrieval Augmented Neural Machine Translation: A Systematic Comparison,” arXiv preprint arXiv:2404.02835, 2024.

더 이상 사람이 태그 규칙을 직접 작성하지 않습니다. 기존 번역 파일에서 LLM이 자동으로 태그 규칙을 추출하고 검증까지 끝냅니다.

기존 번역에 같은 문장이 있으면 번역 파이프라인 없이 그 번역이 그대로 나옵니다.

판별하지 못하는 태그를 사람이 few-shot 예시로 넣어 주지 않습니다.

용어집

별도 서비스로 분리해 공통 API로 제공

직접 구현

용어는 엑셀, 매칭 엔진은 기계번역 안에 박혀 있어, 매칭 하나 고치려면 기계번역을 통째로 재배포해야 했습니다.

매칭은 용어와 글자가 같은 자리를 찾은 뒤 앞뒤 글자만 보는 방식이었습니다. 문맥을 보지 않아, 같은 글자가 다른 뜻으로 쓰여도 용어로 잡히는 구조였습니다. 잡힌 용어는 번역 프롬프트에 그대로 들어갔습니다.

번역이 끝난 뒤 용어가 실제로 반영됐는지 확인하는 단계도 없었습니다.

기계번역뿐 아니라 교정·평가와 앞으로 추가할 서비스도 같은 용어집을 사용할 수 있게 했습니다. 관리할 서비스가 하나 늘더라도, 용어 데이터와 매칭 기능을 별도 서비스로 분리해 공통 API로 제공하기로 했습니다.

엑셀로 관리하던 용어를 DB에서 관리하도록 바꾸고, 단일 Cloud Run Service에 용어 조회·매칭 API를 구현했습니다. 기계번역·교정·평가가 이 API를 호출하도록 연결했습니다.

매칭 하나 고치려면 기계번역을 통째로 재배포용어 조회·매칭은 독립 API, 기계번역·교정·평가가 이 API를 호출

평가

외주 검수를 LLM 평가기로 대체

팀원과 공동 구현

품질 확인이 외주 검수(2주~한 달, 분기 1회)라, 모델을 바꿔도 다음 분기에야 결과를 알 수 있었습니다. 새 모델이 나와도 기존 모델보다 나은지 빠르게 확인할 수 없었습니다.

사내에는 기존 채점 기준과 수년간 쌓인 사람 채점 데이터가 있었습니다. LLM이 같은 기준으로 채점하게 하고, 그 결과를 사람 채점과 대조하면 자동 평가를 도입할 수 있는지 검증할 수 있다고 봤습니다.

팀원과 함께 LLM 평가기를 만들었습니다. 태그·숫자·미번역 오류는 코드로 검사하고, 오역·누락·문법 등 판단이 필요한 오류는 LLM이 채점하도록 구현했습니다.

개발 중 사람 채점과 비교하면서, 숙련된 평가자 사이에서도 점수 차이가 있다는 점을 확인했습니다. 이에 특정 평가자의 점수를 맞추기보다 평가기와 사람의 점수 차이가 사람 간 편차 범위 안에 드는 것을 목표로 정했습니다.

엑셀 안에서 이미지가 놓인 위치를 알 수 있으니, 원본 파일을 따로 가공하지 않고 용어와 이미지를 함께 DB에 적재할 수 있다고 봤습니다.

용어집은 보통 수백~수천 항목이라, 저장 시점마다 전체를 스냅샷으로 남기고 복원 시 통째로 갈아 끼워도 부담이 작다고 판단했습니다. 스냅샷은 복원할 때만 읽으므로 DB 대신 GCS에 파일로 두기로 했습니다.
용어 자동 번역
새로 추가한 언어의 용어도, 기존에 등록된 다른 언어의 용어를 참고하면 LLM으로 초안을 만들 수 있다고 봤습니다.

헤더와 언어 열을 자동 인식해 프리셋을 직접 만들 필요를 없앴습니다. 이미지가 포함된 용어집 등록, 저장 시점으로 복원, 새 언어의 용어 초안 자동 번역도 구현했습니다.

장애 진단직접 구현

장애가 발생했을 때 작업 ID만 넣어주면 장애 원인을 진단해주는 클로드코드 스킬을 만들었습니다. 장애가 날 때마다 로그를 직접 읽고 원인을 추정하던 일을 이 스킬이 대신합니다.

  • 로그 통합: 번역 한 건은 라우터와 Service, Job, 샤드를 거치며 로그가 흩어집니다. 모든 로그에 작업 ID를 넣고 같은 형식으로 남긴 뒤, 작업이 끝나면 ID 단위로 합쳐 GCS에 둡니다. GCP 로그 라우터는 시간 단위 파일로 내보내 다른 작업의 로그와 섞이므로 쓰지 않았습니다.
  • 요약 파일: 로그를 합칠 때 오류와 경고가 난 줄 번호, 단계와 언어별 구간, LLM 비용을 요약 파일에 함께 적습니다. 스킬은 이 파일부터 읽어 오류가 난 자리로 바로 갑니다.
  • 로그 없이 죽은 경우: 메모리 초과나 시간 초과로 강제 종료되면 통합 로그가 남지 않습니다. 이때는 Cloud Logging의 컨테이너 로그로 내려가 확인합니다.
  • 진단 결과: 증상별 원인과 의심 코드 위치를 표로 갖고 있어, 결론 한 줄과 근거가 된 로그, 의심 코드 위치를 냅니다. 코드는 고치지 않습니다.
기계번역직접 구현

번역 전에는 깨질 수 있는 태그를 가려두고 용어집·유사 문장·캐릭터 페르소나를 모아 프롬프트를 조립합니다. 번역 후에는 결과를 그대로 믿지 않고 검사와 리플렉션을 거칩니다.

  • 무결성 검사 · 리플렉션: 가려둔 태그가 그대로 돌아왔는지, 변수가 같은 수로 남았는지, 용어를 빠뜨리지 않았는지 코드로 검사합니다. 실패한 항목만 LLM이 수정하고 다시 검사합니다. 루프가 끝나도 결함이 남으면 결함이 가장 적은 후보를 내보냅니다. 결과에 따로 표시하지는 않고, 이런 건은 로그에 남겨 얼마나 나오는지 봅니다.
  • 문장 묶기: 일정 구간 단위로 대화와 비대화를 분류하고 같은 성격끼리 붙여 한 번에 보냅니다. 분류에 실패한 구간은 비대화로 처리해 멈추지 않고 넘어갑니다.
  • 모델 라우팅: 언어쌍마다 평가기 점수가 가장 높은 LLM을 씁니다.

LLM 기반 태그 규칙 생성직접 구현

기존 번역 파일을 등록하면 전처리에서 태그 규칙을 만듭니다. 번역 때는 정규식과 태그 목록을 같이 씁니다.

  • 후보 추출과 판정: 원문에서 [ ], { }, < >로 감싸인 문자열을 태그 후보로 전부 뽑고, 같은 줄의 번역문에서 그 문자열이 어떻게 되었는지 봅니다. 번역문에도 글자 그대로 남아 있으면 태그입니다.
  • 규칙 작성: Claude가 규칙을 작성합니다. 규칙성이 있으면 정규식으로 쓰고, 없으면 태그 목록에 하나씩 적습니다.
  • 검증과 수정: Gemini가 그 규칙으로 후보 전체를 문장, 번역과 함께 훑어 검증합니다. 틀린 곳이 있으면 무엇이 틀렸는지 서술하고, Claude가 그 서술을 보고 규칙을 고칩니다.

      게임별 전처리직접 구현

      기계번역의 전처리 단계입니다. 기계번역이 프롬프트에 넣는 유사 문장·캐릭터 페르소나·태그 규칙이 만들어지는 곳입니다. 게임에 쌓인 기존 번역 파일을 한 번 처리해 두고, 이후 번역은 그 결과를 가져다 씁니다.

      • 전처리 결과물
        • 태그 규칙 — LLM 기반 태그 규칙 생성 항목에서 설명합니다.
        • 캐릭터 페르소나 — 캐릭터별로 대사를 모아 LLM이 말투 설명을 만들어 둡니다.
        • 벡터 인덱스 — 문장을 임베딩해 두고, 번역할 때 비슷한 문장을 찾아 예시로 넣습니다.
        • 캐릭터별 대사 — 대사를 캐릭터별로 묶어 둡니다. 번역할 파일에 캐릭터 정보가 제공되면 그 캐릭터의 대사를 예시로 넣어 말투를 맞추고, 캐릭터를 모르면 벡터 검색으로 찾은 비슷한 문장을 대신 씁니다.
      • 한 번 전처리한 파일은 결과를 저장해 두고, 같은 내용의 파일이 같은 언어로 다시 들어오면 전처리를 건너뜁니다.
      • 전처리가 실패하면 그 결과물 없이 로그만 남기고 본 번역은 그대로 진행합니다.

      전처리 흐름

      용어집직접 구현

      매칭은 용어집으로 미리 만든 Aho-Corasick 매칭 인덱스로 합니다. 용어집이 크면 이 인덱스를 만드는 비용이 커서, 한 번 만든 인덱스를 메모리와 GCS에 저장해 두고 용어가 바뀔 때만 다시 만듭니다.

      러시아어를 포함한 일부 유럽어는 같은 단어라도 문장 안에서 문법적 역할에 따라 형태가 달라지는 격변화가 존재합니다. 형태가 바뀌면 용어를 썼는데도 못 썼다고 판정될 수 있어서, 언어별 형태소 분석기로 기본형을 미리 계산해 저장하고 검사할 때 같은 규칙으로 비교합니다.

      시스템 아키텍처

      평가팀원과 공동 구현

      수년 전부터 국제 표준 MQM을 사내 기준으로 변환한 채점 체계가 이미 있었습니다. 기존에는 사람이 그 기준대로 기계번역 결과를 채점했고, 지금은 평가기가 같은 기준으로 채점합니다.

      • 검증: 평가기는 오류 항목을 먼저 산출하고, 항목별 감점을 합산해 100점에서 차감합니다. 기존 사람 채점 데이터와 대조해 오류 항목의 일치 여부를 확인했고, 평가기와 사람의 최종 점수 차이가 사람 평가자 간 점수 차이 범위에 들어오는 것을 확인했습니다.
      • 판정 구조: 태그·숫자·미번역처럼 답이 정해진 오류는 코드가 잡습니다. 오역·누락·문법처럼 판단이 필요한 오류와 용어 위반은 LLM이 잡습니다. 채점 LLM은 하나로 고정해 두어, 어떤 모델이 번역했든 같은 기준으로 점수가 나옵니다.

        채점 모델은 번역 후보들끼리 서로의 번역을 채점하게 해 보고 골랐습니다. Gemini는 자기 번역에 눈에 띄게 후한 점수를 줬고, Claude는 그 편향이 가장 작았습니다. 그래서 Claude를 채점 모델로 정했고, 채점에 쓰는 버전은 번역에는 쓰지 않습니다. 번역은 다른 버전의 Claude와 Gemini가 맡습니다.

        채점할 때는 LLM에게 그 문장의 지정 용어를 미리 알려 주고, 감점마다 어느 부분이 왜 틀렸는지 적게 합니다. 게임 번역은 지정 용어를 정확히 쓰는 것이 가장 중요한데, LLM은 그 용어가 어색하다며 자연스러움 점수를 깎기도 합니다. 용어를 제대로 썼는데 받는 억울한 감점입니다. 그래서 감점 목록에서 지정 용어를 올바르게 썼는데 그 용어를 문제 삼은 항목은 코드가 점수 계산에서 뺍니다. 합격선 근처 점수는 한 번 더 채점해 두 점수 중 낮은 쪽을 택하고, 두 점수가 크게 다르면 세 번째 채점까지 해서 중앙값을 씁니다.
      • 한계: 억울한 감점을 점수 계산에서 빼려면 코드가 번역문 안에서 지정 용어를 찾아내야 합니다. 게임 창작어는 사전에 없고 러시아어 같은 언어에서는 어미가 문장마다 바뀌어서, 처음에는 코드가 못 찾는 형태가 있었습니다. 실제로 발생한 경우는 격변화 규칙을 보강해 잡고 있습니다. 다만 아직 보지 못한 형태가 남아 있을 수 있어, 격변화를 판단하는 LLM 단계를 하나 더 두는 것을 검토하고 있습니다.

      사용성직접 구현

      기획자와 함께 파일 입력과 용어집 등록 절차를 개선하고, 지원 문서 형식과 번역 실행 방법을 늘렸습니다.

      • 프리셋 자동 인식 — 기존 용어집과 번역 파일에서 언어 코드 표기를 모아 사전으로 만들었습니다. 헤더와 언어 열은 먼저 이 사전과 규칙으로 판별하고, 걸리지 않는 열만 주변 행·열과 함께 LLM에 보냈습니다. 이 인식 과정은 시트 번역과 용어집 등록이 함께 씁니다. 여러 파일의 일괄 업로드도 지원합니다.
      • 이미지 용어집 — 용어를 먼저 추출해 ID를 생성하고, XML을 읽어 이미지를 행·열 위치에 맞는 용어에 저장합니다. 이후 재등록·편집·내보내기 모두 이 연결을 기준으로 동작합니다. 재등록은 셀 단위 병합, 편집은 지정한 셀만 교체, 내보내기는 DB의 배치와 이미지로 xlsx를 다시 만듭니다.
      • 용어집 롤백 — 편집이나 파일 등록으로 용어집이 바뀔 때마다 전체 용어와 시트·열 구조를 JSONL.gz로 묶어 GCS에 저장했습니다. 복원은 용어집에 잠금을 걸어 편집을 막은 뒤 기존 용어를 지우고 스냅샷을 넣는 방식입니다.
      • 용어 자동 번역 — 언어 열을 추가하고 자동 번역을 누르면 빈칸을 배치 단위로 번역합니다. 이때 다른 언어의 용어도 함께 LLM에 보여 줍니다. 결과는 사용자가 확인한 뒤에 저장합니다.
      • 문서 번역 — 게임 텍스트 외 사업부 문서까지 대상을 넓혔습니다. 워드·파워포인트·마크다운·txt 문서까지 형식에 맞춰 번역해 줍니다.
      • 스킬 배포 — 플랫폼 웹에 접속하지 않아도, Claude Code 같은 AI 도구에서 바로 번역할 수 있는 스킬을 배포했습니다.
